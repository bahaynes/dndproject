# Plan: MCP server with OAuth

Status: **draft; protected-auth section approved by Ben 2026-11-26; questions 1–5 decided; lifetime numbers and question 6 still open.** Nothing here is built.

**Unblocked (2026-11-26):** the privacy policy (#163) and terms of service (#164) pages shipped in #165. The MCP connector sends campaign data to whatever app a GM connects; `/privacy` now discloses this under "Connected apps".

## Goal

Let Claude (Claude Code, and claude.ai as a connector) read and edit a campaign's board through a proper remote MCP server. A GM adds one URL, logs in with Discord in a browser, approves the connection, and Claude can then:

- read missions, sessions and sign-ups, items and factions;
- draft missions, always created hidden, so a GM publishes them by hand;
- link a mission to the Foundry one-shot module that runs it (`oneshot-<slug>` in the foundry-oneshots repo).

## Decisions already made

- **The authorization server lives inside the backend on Cloud Run.** Authelia on the homeserver was ruled out: it would make the home network a failure point for GCP, and it probably needs clients configured in advance, which doesn't suit MCP clients that register themselves.
- **Discord is the identity provider only.** The backend runs its own OAuth 2.1 authorization server and issues its own tokens. Discord confirms who the user is during `/authorize` and plays no further part.
- **We implement the spec as of MCP 2026-07-28** (authorization section), with the official Python SDK `mcp` v2.x (`MCPServer`) as the resource server.

## This touches the protected auth area

`CLAUDE.md` says auth is protected and must not change without an explicit task. This plan is that task, but it is written to leave the existing contract alone:

- No change to `frontend/src/lib/auth.ts`, `+layout.svelte`, `localStorage` tokens, or the `/login/callback` → `/campaigns` flow.
- No change to `get_current_active_user` / `get_current_active_admin_user`. MCP requests are authenticated by the SDK's `TokenVerifier`, not by a new FastAPI dependency.
- MCP tokens are a separate kind of token: their own signing key, `aud` set to the MCP URL, and their own lifetimes. Frontend JWTs are rejected at `/mcp`, and MCP tokens are rejected everywhere else.
- **Shared code:** the guild-role check in `campaigns/router.py` `join_campaign` (bot token → member roles → `dm_role_id` / admin role names → `"admin"`) moves into a service function, which `/campaigns/join` and the MCP consent step both call. This is the only refactor of existing auth-adjacent code. It gets its own commit, and the existing tests must pass unchanged.

*Approved by Ben, 2026-11-26.*

## How the spec maps onto this app

Public origin: `https://westmarches.bahaynes.com`. The frontend Caddy (`Caddyfile.cloudrun`) proxies `/api/*` to the backend service.

| Spec piece | Here |
|---|---|
| MCP endpoint (resource server) | `https://westmarches.bahaynes.com/api/mcp` |
| Protected Resource Metadata (RFC 9728) | `/.well-known/oauth-protected-resource/api/mcp`, generated by the SDK from `AuthSettings` |
| Authorization server issuer | `https://westmarches.bahaynes.com` |
| AS metadata (RFC 8414) | `/.well-known/oauth-authorization-server` |
| Endpoints | `/api/oauth/authorize`, `/api/oauth/token`, `/api/oauth/revoke`, and `/api/oauth/register` only if needed (see open questions) |

**Caddy change:** `/.well-known/oauth-*` currently falls through to the SvelteKit file server. Add a matcher that proxies those paths to the backend as well, in both `Caddyfile` and `Caddyfile.cloudrun`.

## Components

### 1. Resource server: `/api/mcp`

- An `MCPServer` mounted in the FastAPI app with Starlette `Mount`, before any catch-all route. The app lifespan enters `mcp.session_manager.run()`; a mounted sub-app's lifespan never runs by itself.
- `AuthSettings(issuer_url=<origin>, resource_server_url=<origin>/api/mcp, required_scopes=["board:read"], validate_token_resource=True)`.
- `transport_security=` must allowlist `westmarches.bahaynes.com` and the `*.run.app` host. Without it, every request gets HTTP 421.
- **Stateless transport.** Cloud Run runs several instances, and each runs 2 gunicorn workers. Nothing may live in process memory between requests: MCP sessions run in the SDK's stateless HTTP mode (check its exact name in v2), and all OAuth state (codes, refresh tokens, pending authorizations) lives in Postgres.
- `McpTokenVerifier.verify_token`: decode the JWT with `MCP_TOKEN_SECRET`; check `iss`, `aud == <origin>/api/mcp` and `exp`; check the token's grant row is not revoked; return an `AccessToken` carrying the scopes, plus the user and campaign in claims.
- Tools read the user, campaign and scopes from `get_access_token()`. Each write tool **also** re-checks in the database that the user is still `admin` in that campaign. A scope says what the client may ask for; the database says what the user may do.
- A missing or invalid token gets 401 with `WWW-Authenticate: Bearer resource_metadata=…, scope="board:read"` (the SDK does this). A tool needing a scope the token lacks returns 403 `insufficient_scope` naming the scope, which lets the client step up.

### 2. Authorization server

**Library: Authlib** (*decided 2026-11-26*). The MCP SDK's own authorization server (`auth_server_provider=`) is out: its docs say it "predates the AS/RS separation that the MCP authorization spec is built around. New servers should not reach for it." The SDK stays as the resource server only. Python has no FastAPI-blessed authorization server, so we use the most widely used maintained one: Authlib (BSD licence, frequent releases).

- **Adapter.** Authlib ships server integrations only for Flask and Django. We write a small FastAPI adapter: a subclass of its framework-agnostic `AuthorizationServer` that turns a Starlette request into an Authlib request and an Authlib response into a Starlette response. Its Flask integration is the model to copy. Keep the adapter in its own module with its own tests.
- **Authlib provides:** the authorization-code and refresh-token grants, PKCE (`CodeChallenge`, with PKCE required for every client; check that it can be held to S256 only, or reject `plain` ourselves), RFC 7009 revocation, RFC 8414 metadata and RFC 9207 `iss` (`IssuerParameter`).
- **We still write:** CIMD client loading (Authlib's client lookup calls our function, which fetches and validates the document), the `resource` binding (RFC 8707: Authlib's server doesn't cover it, so we check `resource` at authorize and token and store it on the code and grant), refresh rotation with reuse detection (in the grant's storage hooks), the Discord leg, the consent page and the campaign role check.
- **Version:** pin the latest stable 1.x release on PyPI (not a beta) when building, and check the changelog for the PKCE API. `CodeChallenge(required=True)` is deprecated in favour of overriding `is_code_challenge_required`.

**`GET /.well-known/oauth-authorization-server`** returns `issuer`, `authorization_endpoint`, `token_endpoint`, `revocation_endpoint`, `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, `code_challenge_methods_supported: ["S256"]` (clients refuse to continue without it), `token_endpoint_auth_methods_supported: ["none"]`, `scopes_supported`, `client_id_metadata_document_supported: true`, and `authorization_response_iss_parameter_supported: true`.

**`GET /api/oauth/authorize`**

1. Validate the client:
   - **CIMD only** (*decided 2026-11-26*; no `/register`): `client_id` is an HTTPS URL. Fetch it (with timeout, size cap and a short cache), require its `client_id` to equal the URL exactly, and require `redirect_uri` to be in its `redirect_uris`. Refuse URLs that resolve to private, loopback or link-local addresses (SSRF), and don't follow redirects to them.
   - `redirect_uri` must be HTTPS or `http://localhost`/`127.0.0.1`.
   - If the client or the redirect URI is invalid, show an error page and **do not redirect**.
2. Require `code_challenge` with `code_challenge_method=S256`, require `resource == <origin>/api/mcp`, and check the requested `scope` against `scopes_supported`.
3. Store a pending authorization row keyed by a random ID, then send the user through Discord login (step 4).
4. **Discord leg:** a new `/api/oauth/discord/start` and `/api/oauth/discord/callback`, separate from the frontend's `/api/auth/discord/*`. They use the same Discord application with its own `state` and nonce cookie. Discord gives identity (`identify`, plus `guilds` to list campaigns).
   - **Second redirect URI** (*decided 2026-11-26*), not `proxy-callback`: Ben adds `https://westmarches.bahaynes.com/api/oauth/discord/callback` (and `http://localhost:8000/api/oauth/discord/callback` for local dev) in the Discord developer portal. `_is_allowed_proxy_callback` stays unchanged. As a result, MCP login doesn't work on PR previews; preview testing goes through Playwright and dev login instead.
5. **Consent page**, server-rendered HTML from the backend (not SvelteKit, so the frontend auth contract stays untouched). It shows:
   - the client name and the **redirect hostname** (the spec requires it), with an extra warning when the redirect is localhost;
   - a campaign picker, listing only campaigns where the shared role check says `admin`;
   - the scopes, in plain words.

   Consent is **required for every new client** before Discord is involved for that client. This is the spec's confused-deputy rule: we use one static Discord client ID for every MCP client that registers itself. Remember consent per (user, client_id, campaign, scopes) so reconnecting doesn't ask again.
6. On approval, issue a single-use authorization code bound to client_id, redirect_uri, code_challenge, resource, user, campaign and scopes, with a short expiry. Redirect with `code`, `state` and `iss`. Errors also carry `iss`.

**`POST /api/oauth/token`**

- **`authorization_code`:** verify the PKCE `code_verifier` and that client_id, redirect_uri and resource match the code. Burn the code; a reused code revokes everything it issued. Return:
  - an access token: a JWT with `iss`, `sub` (user id), `aud` (MCP URL), `campaign_id`, `scope`, `client_id`, `grant_id` and a short `exp`;
  - a refresh token: an opaque random string, stored hashed.
- **`refresh_token`:** **rotate every time.** This is a MUST for public clients. Issue a new refresh token, invalidate the old one, and treat reuse of an old one as theft: revoke the whole grant. A refresh can't add scopes beyond the original grant. Before issuing, re-check that the user is still admin in the campaign.

**`POST /api/oauth/revoke`** (RFC 7009) revokes a grant by refresh token.

### 3. Data (Alembic migration)

- `oauth_clients`: a cache of fetched CIMD documents: client_id (the URL), name, redirect_uris, fetched_at.
- `oauth_pending_authorizations`: id, client_id, redirect_uri, state, code_challenge, resource, scopes, user_id (null until login), campaign_id, expires_at.
- `oauth_codes`: code hash, grant fields, expires_at, used_at.
- `oauth_grants`: id, user_id, campaign_id, client_id, scopes, created_at, revoked_at. One row per connection, which a "connected apps" list can show and revoke.
- `oauth_refresh_tokens`: token hash, grant_id, issued_at, expires_at, replaced_by, used_at.
- A cleanup step for expired pending authorizations and codes: on each `/authorize`, or a periodic job.

### 4. Settings

`MCP_TOKEN_SECRET` (separate from `SECRET_KEY`, at least 32 characters, required in production), `PUBLIC_ORIGIN`, and the token lifetimes below. Production values go in Cloud Run secrets.

### 5. Scopes

- `board:read`: list and get missions, sessions with sign-ups, items, factions.
- `board:write`: create and update missions and set their one-shot link. Implies `board:read`; the spec requires servers to honour scope hierarchies.

`scopes_supported` advertises both. `offline_access` is **not** advertised in PRM or in challenges, per the spec. Write scopes are offered only to campaign admins on the consent page.

### 6. Tools (first cut)

| Tool | Scope | Wraps |
|---|---|---|
| `list_missions(status?, include_retired?)` | read | `missions` service |
| `get_mission(id)` | read | `missions` service |
| `list_sessions(upcoming_only?)` with sign-ups | read | `sessions` service |
| `list_items`, `list_factions` | read | their services |
| `create_mission(...)` | write | `missions` service, **forced hidden**: `is_discoverable=false`, which non-admins can't see (`missions/service.py`, `router.py`) |
| `update_mission(id, ...)` | write | `missions` service; may not change visibility or status. `update_mission` in the service copies `is_discoverable` from the payload, so the tool must pass the current value through |
| `set_mission_module(id, module_id)` | write | new column below |

Not exposed: admin import/export, reward distribution, ledger writes, campaign settings, member roles.

Tools call the existing service functions, not the HTTP routes, so validation and ledger rules apply. They must not query models directly where a service already exists.

**New column:** `missions.foundry_module` (nullable string, e.g. `oneshot-gilded-moth`), shown read-only on the mission page.

### 7. Client side

- Claude Code: `claude mcp add --transport http westmarches https://westmarches.bahaynes.com/api/mcp`, or an entry in foundry-oneshots `.mcp.json`. The first call opens the browser login.
- claude.ai: add a custom connector with the same URL.

## Build order (one commit each)

1. Refactor the guild-role check into a service function; existing tests unchanged.
2. Migration and models for the OAuth tables, plus `missions.foundry_module`.
3. Authlib FastAPI adapter, with tests. Then AS metadata, `/authorize` (CIMD client loading, PKCE, `resource`, pending row), Discord leg, consent page, code issue.
4. `/token` (code and refresh with rotation and reuse detection) and `/revoke`.
5. Mount `MCPServer` with the verifier, `transport_security` and stateless mode; Caddy `.well-known` routing; read tools.
6. Write tools, the admin re-check, and the forced-hidden rule.
7. E2E: a scripted OAuth client (PKCE, CIMD from a local fixture URL) against the dev pod, then a real connect from Claude Code against a preview deploy.

## Tests

- Unit tests:
  - PKCE verify;
  - CIMD `client_id` mismatch rejected; redirect URI not in the document rejected;
  - `resource` mismatch rejected at authorize and token;
  - code reuse revokes the grant; refresh reuse revokes the grant;
  - wrong-`aud` and frontend JWTs rejected at `/mcp`;
  - a player (not admin) can't get `board:write`; a demoted admin can't refresh or write.
- Integration: 401 carries `resource_metadata`; 403 `insufficient_scope` on a write with a read-only token.
- Regression: the frontend login flow e2e tests still pass unchanged.

## Open questions for Ben

1. **Token lifetimes.** *Decided (2026-11-26):* longer access tokens (revocation is already checked per request via the grant row). Lifetimes are settings; the numbers are still Ben's to pick.
2. **Client registration.** *Decided (2026-11-26):* CIMD only. No `/register`. Clients that only do DCR are unsupported. Still confirm with a logging stub that current Claude Code and claude.ai send a CIMD `client_id`; if one of them doesn't, it can't connect.
3. **Discord redirect.** *Decided (2026-11-26):* a second redirect URI. MCP login won't work on PR previews.
4. **Players.** *Decided (2026-11-26):* GMs only. `board:read` for players can come later as an additive change.
5. **Library.** *Decided (2026-11-26):* Authlib, with a small FastAPI adapter (see section 2).
6. **Concurrent refresh.** Several Cloud Run instances can get two refreshes with the same token at once, and reuse detection would then revoke the grant. Allow a short grace window for the token just replaced (how long is Ben's call), or accept the occasional forced re-login?
